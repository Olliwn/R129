### August 9, 2026 (Sunday) — Touchscreen found disconnected (root cause of "unresponsive UI"); blueman popups disabled; pending touch-menu build deployed

First head-unit session since May 27. Started as "there's a popup I can't bypass", turned into two genuinely separate problems plus a deploy that had been sitting undelivered since May.

**Headline: the UI was unresponsive because the touchscreen is not connected to the Pi at all.** The popups were real and worth removing, but they were a red herring — see the correction section below.

#### Symptom 1 — "active pop up window that I do not manage to bypass"

Car parked outside with the Pi powered. Pi reachable at `192.168.1.36` via `r129.local`, uptime 3 min (fresh boot). A `grim` screenshot over SSH showed popups immediately: **two stacked `blueman-applet` notification windows** ("iPhone / Disconnected") floating in the middle of the display, over the R129 wireframe. `wlrctl window list` confirmed three windows — the R129 UI plus two `blueman-applet: iPhone`.

These are desktop Bluetooth notifications from the Raspberry Pi OS BT applet, not anything in the R129 UI. They float above the Qt surface and take Wayland focus, so they *were* worth eliminating on a head unit. The UI process itself was healthy the whole time (`r129-ui.service` active, PID 1455 alive, wireframe still animating).

#### Fix — kill the applet, disable it permanently

`blueman-applet` is **redundant on this system**: Bluetooth pairing is already handled headlessly by `~/.config/systemd/user/bt-agent.service` (`bt-agent --capability=NoInputNoOutput`, active + enabled). The applet contributes nothing but popup noise on a head unit with no desktop.

1. Killed `blueman-applet` (PID 1177) and `blueman-tray` (PID 1347).
2. Disabled autostart with a user-level override shadowing `/etc/xdg/autostart/blueman.desktop`:

```ini
# ~/.config/autostart/blueman.desktop
[Desktop Entry]
Type=Application
Name=blueman-applet
Exec=/usr/bin/blueman-applet
Hidden=true
X-R129-Note=Disabled for the car head unit: blueman popup notifications float
 over the R129 UI and steal touch focus. Bluetooth pairing is handled
 headlessly by bt-agent.service (NoInputNoOutput), so the applet is redundant.
```

`Hidden=true` in the user autostart directory suppresses the system-wide entry without touching `/etc`, so an OS package update won't silently re-enable it and we haven't diverged from the distro's files.

Post-fix `wlrctl window list` shows only `python3: R129 Driver UI`. Screen clean.

#### Symptom 2 (the actual root cause) — touchscreen never enumerated

**Correction to the first diagnosis this session.** With the popups gone the screen was still completely unresponsive — no menu navigation, no drag on the Home wireframe. The popups had been assumed to be the cause of the unresponsiveness; they were not. They were a coincident, separate annoyance.

Real cause, established in three checks:

| Check | Result |
| :--- | :--- |
| `sudo dmesg \| grep -i 0712` | **`NEVER ENUMERATED`** — the Waveshare touch controller (`0712:000a`) has not appeared once since boot |
| `/proc/bus/input/devices` | Only `pwr_button`, `vc4-hdmi-0/1` (CEC), the two HDMI-jack switches, and a virtual `iPhone (AVRCP)` node. **No touch device at all.** |
| `lsusb` / port walk | Only `2e4f:4002` (Audiotec Fischer DSP) on `3-1` and `1314:1520` (Carlinkit) on `3-2`. Both remaining Pi USB ports empty. |

The compositor has no touch device to read, so no amount of software work can help. Software side confirmed intact and *not* the problem: `autotouch` still installed (`ii autotouch 0.1`), kanshi rotation profile unchanged (`transform 90`), UI service healthy.

**Key discriminator: the panel is lit and rendering, but touch is dead.** Per `work/display_mount/README.md` the panel exposes *two* micro-USB ports — one **touch + power**, one **power-only** (documented as unused) — plus 180° adapters redirecting connectors rearward. A lit panel with dead touch means power is arriving while the USB data lines are not working. Three candidates, most likely first after a ~10-week layoff in a car:

1. Cable is in the **power-only** micro-USB port instead of the touch/power port.
2. Micro-USB connector or its 180° adapter has vibrated **partially loose** — outer power pins still contact, inner data pins do not. Very common failure mode for micro-USB under vibration.
3. **Cable failure or a charge-only cable.** Step 6 of the bring-up plan already records that *"the first two USB cables tried were charge-only (no data lines); the third cable worked"* — this trap has bitten this exact build once before.

**Diagnostic caveat worth remembering:** `grim` captures the *compositor framebuffer*, not the physical panel. A clean screenshot proves the Pi is rendering; it says nothing about whether the panel is lit or the touch digitiser is alive. Owner confirmed visually that the panel is lit.

Resolution pending physical access — re-seat both ends of the touch cable (verifying it's in the touch port, not power-only), try a different Pi USB-A port, then a known-good data-capable cable. A live `dmesg -w` filter on `0712|input: ` was left running to catch the moment it enumerates.

##### Gotcha repeated: pgrep/pkill self-match killed the SSH session (again)

Same trap as the May 27 session, in a new costume. The kill command used:

```bash
PIDS=$(pgrep -f "blueman-applet|blueman-tray")
```

`pgrep -f` matches against full command lines — including the command line of the `bash -c` wrapper that SSH spawned, which literally contains the string `blueman-applet|blueman-tray`. So the pattern matched its own shell (PIDs 3175/3176 appeared in the kill list alongside the two real targets) and the session died with exit 255. The applet did get killed, but the connection dropped mid-command.

**Standing workaround for this repo:** wrap one character of the pattern in a single-character class so the regex still matches the target but the literal command line does not match the regex:

```bash
pgrep -af "blueman-[a]pplet|blueman-[t]ray"
```

`blueman-[a]pplet` matches the string `blueman-applet`, but the command line contains `blueman-[a]pplet`, which the regex does not match. Used for every subsequent process query this session with no further self-kills. Worth using by default on this Pi given how often we grep for processes over SSH.

#### Deployed the pending touch-menu build

The May 27 commit `ab16470` had the touch-operable menu work committed but never rsynced to the Pi (the deploy attempt hung because the car had already been driven out of Wi-Fi range). Pushed it now — 7 files: `diag_view.py`, `exit_view.py`, `main_window.py`, `settings_view.py`, `sidebar.py`, `split_pane_view.py`, `theme.py`.

Deploy procedure used (worth keeping as the standard):

1. `rsync -avzn` **dry run first** to confirm the file list matches expectation.
2. `rsync -avz` for the real transfer.
3. **`python3 -m py_compile *.py` on the Pi before restarting the service** — catches a syntax error while the old UI is still running, instead of discovering it after the restart leaves a dead head unit in a car that may be out of network range. Cheap insurance; adopt as standard.
4. `systemctl --user restart r129-ui.service`.

All files compiled clean; service restarted to PID 3546.
